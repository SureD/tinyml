Implementation Proposal

Metal Backend Optimization

目标不是先做一轮大而全的 profiling，而是先从 Metal 执行模型、 M5 硬件约束和 TinyLlama 的实际矩阵形状，推导出当前实现中确定存在的问题。

Status: Proposed Target: Apple M5 / Metal 4 Model: TinyLlama 1.1B Scope: infer/src/metal_backend.mm

结论先行

1. 不应每个 op 都等待 GPU

同一 serial compute pass 内的 dispatch 已按顺序处理依赖。 每个 op 调用 waitUntilCompleted 是 CPU 等待，不是算子依赖所必需的同步。

2. Matmul 至少分成三条路径

M=1 用带宽型 GEMV，M=2..8 用 small-batch GEMV，较大的 M 才进入 tiled GEMM / Metal 4 MPP。

3. 先合并提交，再融合 kernel

第一层收益来自一次提交多个 dispatch。随后再做 QKV、gate/up、 matmul epilogue 和 decode attention 的数据流融合。

4. 精度是最后一层优化

FP16 能把权重流量减半，但不能修复错误的同步、跨行访存和多余中间张量。 先把执行结构做对，再切 FP16。

0. 推导起点：M 决定复用，M5 决定映射

所有优化都从同一个矩阵乘法开始。TinyLlama 的线性层执行：

X[M,K] × W[N,K]ᵀ → Y[M,N]

M = 本次同时处理的 token 数
K = 输入 hidden dimension
N = 输出 dimension
M 的范围 硬件行为 kernel 目标
M=1 每个权重只服务一个 token，几乎没有层内复用 减少字节数，保证连续/向量化 load，用足内存带宽
M=2..8 已有少量权重复用，但不足以摊薄完整 GEMM tile 的固定成本 一次权重 load 同时累积多个 token 的 small-batch GEMV
M>8 权重可被多个 token 重复使用，arithmetic intensity 上升 二维 tiled GEMM；对齐且 M≥32 时进入 Metal 4 MPP
统一原则： Decode 优化的是“每字节完成更多有效工作之前，先把字节连续地送进来”； Prefill 优化的是“同一份权重送进来一次，尽量服务多个 token”。 cache 和 threadgroup memory 都只是实现复用的手段，不是目标本身。 
if (M == 1)                 → GEMV
else if (M <= 8)            → small-batch GEMV
else if (M >= 32 && aligned
         && fp16_mpp)      → Metal 4 matmul2d
else                        → tiled GEMM fallback

“多少个 group”要分三层回答

8 个 GPU core                         // 物理执行资源
  └─ threadgroup                     // 软件发出，硬件动态调度
       └─ simdgroup = 32 threads     // 锁步执行的基本单位
            └─ lane                  // 一个 Metal thread
  • SIMD group 大小：本机确定为 32 threads。
  • 每个 threadgroup 放多少 SIMD groups：由 kernel 决定。 本设计以 decode 的 8 groups / 256 threads，以及 MPP prefill 的 4 groups / 128 threads 作为起点。
  • 每个 GPU core 同时驻留多少 threadgroups：Apple 没有通过 Metal API 公布固定值；它取决于线程数、寄存器和 threadgroup memory， 必须用 GPU capture/counters 验证。

Decode GEMV 若让一个 256-thread group 协作计算 2 个输出行，则每个 projection 启动的 threadgroup 数为 ceil(N/2)：

Projection N Threadgroups / dispatch
Q / O / Down20481024
K / V256128
Gate / Up56322816
LM head3200016000

这是可解释的首个配置，不是预先宣布的最优值。启动数远大于 8， 才能让调度器持续给 8 个 GPU cores 分配工作。

Prefill 若采用候选的 64×64 threadgroup 输出 tile，则 groups = ceil(M/64) × ceil(N/64)。以 M=128 为例：

Projection Threadgroups 调度含义
Q648 个 core 有多轮工作
K 或 V8 each单独 dispatch 只有一轮，容易被固定开销放大
Packed QKV80合成一个较饱满的 dispatch，并只读取一次 X
Gate 或 Up176 each并行度充分
Packed Gate+Up352总计算量不变，但删除一个 dispatch 和一次 X 读取

M5 仍未公开的参数

Apple 没有公开本机每个 GPU core 的 SIMD 单元数、寄存器文件容量、片上 cache 容量、固定 resident-threadgroup 数和精确 FP32/FP16 峰值。文档不为这些参数填入 猜测值；tile 候选由已知限制生成，最终 occupancy 与吞吐由 profiler 决定。

1. 同步：一个 op 不等于一个提交

当前每个 backend op 都创建 command buffer 和 encoder，编码一个 dispatch， 然后在 commit_and_wait() 中执行 commit + waitUntilCompleted。这会把一层模型切成很多个 CPU/GPU 往返，并使 CPU 无法提前编码后续工作。

当前 encode RMSNorm commit + CPU wait encode Q matmul commit + CPU wait ...
→
目标 begin decode step encode all layer ops encode final argmax commit once + wait for token id

Metal 已经提供哪些同步

机制 作用范围 本项目何时使用
Serial compute dispatch 同一 compute pass 中，前一 dispatch 的写入对后一 dispatch 可见 默认路径；模型算子按顺序编码，不需要每 op CPU wait
memoryBarrier 同一 compute encoder 内的显式内存屏障 只有切换 concurrent dispatch 或手工管理特殊 hazard 时使用
MTLFence 同一 queue 上，不同 encoder/pass 之间 拆分 encoder 且资源使用 untracked hazard mode 时使用
MTLSharedEvent 跨 queue、跨 command buffer 或 CPU/GPU 未来多 queue 或异步流水线；当前单 queue 不需要
waitUntilCompleted 阻塞 CPU，直到整个 command buffer 完成 CPU 真正需要结果时：当前 greedy decode 中每个 token 的最终 token id
设计决定： 第一版保持 tracked resources 和 serial dispatch。每个 prefill 或 decode step 使用一个 command buffer；只在 CPU 读取 argmax 结果时等待。不要提前引入 concurrent dispatch、untracked resources 或多 queue。 
// Execution API: op 只编码，不提交，不等待。
metal_begin_step(ctx);

for (int layer = 0; layer < n_layers; ++layer) {
    metal_encode_rmsnorm(ctx, ...);
    metal_encode_matmul(ctx, ...);
    metal_encode_attention(ctx, ...);
    metal_encode_mlp(ctx, ...);
}

metal_encode_argmax(ctx, ...);
int token = metal_end_step_and_read_token(ctx); // 唯一 CPU wait

2. Matmul：从 M5 和矩阵形状推导

TinyLlama 的线性层权重以 W[N,K] row-major 存储。 结合上一节的 M5 限制，核心 shape 如下。

Projection N × K FP32 / layer 关键特征
Q / O 2048 × 2048 16 MiB each 方阵，decode 和 prefill 都是主路径
K / V 256 × 2048 2 MiB each GQA 小输出维度
Gate / Up 5632 × 2048 44 MiB each MLP 最大的两次输入投影
Down 2048 × 5632 44 MiB K 更大，decode reduction 更长
LM head 32000 × 2048 250 MiB 每个 token 最大的单次权重读取

4.098 GiB 是怎么得到的

设层数 L=22、hidden H=2048、FFN I=5632、词表 V=32000。由于 head_dim=2048/32=64、KV heads 为 4，所以 KV=4×64=256。这与 infer/src/llama.cc::build_memory_plan() 的实际分配公式一致。

部分 参数量公式 参数量
每层 attention + 2 个 norm 2H + 2H² + 2(KV×H) 9,441,280
每层 MLP 3(I×H) 34,603,008
22 层合计 22 × 44,044,288 968,974,336
Embedding + final norm + LM head V×H + H + V×H 131,074,048
全部常驻权重 1,100,048,384 × 4 bytes 4.400 GB = 4.098 GiB

但单个 decode token 不读取全部 4.098 GiB

Decode 会遍历 22 层全部权重和整个 LM head，但 embedding lookup 只读取当前 token 的一行 H=2048，不会扫描 250 MiB embedding table。 在“跨 token 几乎没有 cache 复用”的 streaming 模型中，每个 token 的权重流量 可按下面的式子估算：

decode elements
= 22-layer weights + LM head + final norm + one embedding row
= 968,974,336 + 65,536,000 + 2,048 + 2,048
= 1,034,514,432 FP32 values

bytes = 1,034,514,432 × 4 = 4,138,057,728 bytes
= 4.138 GB = 3.854 GiB

DRAM streaming time ≈ 4.138 GB / 153 GB/s = 27.0 ms/token
corresponding roofline ≈ 153 GB/s / 4.138 GB = 37.0 token/s

这不是每个 token 都把 4.138 GB 上传到 GPU

Apple Silicon 使用 unified memory，CPU 和 GPU 访问同一块物理内存，不存在独立显存， 也没有每个 token 经 PCIe 从 RAM 复制到 VRAM 的过程。当前 backend 在 alloc_arena() 中用 MTLResourceStorageModeShared 创建权重 buffer；checkpoint 加载时 CPU 通过 memcpy 写入一次， 此后权重一直驻留在 unified DRAM 中。 

模型加载一次：
SSD → CPU staging buffer → shared MTLBuffer in unified DRAM

每个 decode token：
同一个 MTLBuffer → memory controller / on-chip caches → GPU registers → FMA
                    ↑
              这里消耗 unified-memory bandwidth

第二条路径不是软件显式执行的“大复制”。matmul shader 发出普通 load， 硬件按 cache line 将需要的权重从 unified DRAM 拉入片上 cache，随后送到寄存器。 cache 的填充和淘汰由硬件完成，Metal 程序不能把 4 GB 权重手工放进“离 GPU 最近的缓存”，片上 cache 也容纳不下整个模型。

153 GB/s 指什么： 它是 unified DRAM 通过内存控制器向 SoC 中 CPU、GPU 等单元提供数据的峰值带宽， 不是 GPU cache 的内部带宽，也不是 CPU 到独立 GPU 的上传带宽。多个硬件单元会共享它。

这里必须用十进制 GB 与厂商标注的 153 GB/s 相除， 不能直接把 GiB 当成 GB。上面的 27.0 ms 不是严格的物理下界，而是一个带假设的 DRAM streaming roofline：假设跨 token 几乎没有权重 cache 命中、 每个相关权重从 DRAM 读取一次，并且 GPU 能持续获得 100% 峰值带宽。若 cache 命中，DRAM 流量会下降；若考虑 activation、KV cache、attention、重复读取和调度， 实际时间会增加。

对本模型，这个估算仍然有工程意义：单 token 权重工作集约 3.854 GiB，远大于片上 cache；而 M=1 时每个矩阵权重只参与一次乘加，层内没有权重复用。 因此 decode 通常接近“顺序流过整套权重”，首先受 unified-memory bandwidth 限制。

Decode：专用 GEMV，lane 沿 K 读取

当前 matmul 让相邻 SIMD lane 计算不同输出行。对固定 k， lane 读取地址相隔一个完整的 K，形成跨行 stride，无法得到理想的 合并访存。正确映射应当是：

  • 一个 threadgroup 协作计算少量输出行，首个候选为 NR=2。
  • 32 个 lane 沿连续的 K 维读取，使用 float4 / half4 向量 load。
  • 每个 lane 累积局部和，先做 SIMD reduction，再跨 SIMD groups 合并。
  • 对 TinyLlama 的 K=2048/5632，从 8 SIMD groups、256 threads 每 threadgroup 起步，以隐藏统一内存延迟。
  • W[N,K] 已适合 GEMV，不为 decode 盲目转置权重。
Shape dispatch： M == 1 直接进入 GEMV kernel。不要让 decode 走带 threadgroup tile 装载和二维输出映射的通用 GEMM。

Small batch：M=2..8 不能直接当大 GEMM

这一区间已经能让一次权重读取服务多个 token，但 token 数太少，完整的 64×64 GEMM tile 会产生大量空位和固定开销。使用 small-batch GEMV： 每个 lane 读取一段连续权重，同时维护 2 到 8 个 token 的 accumulator。

Prefill：二维 tiled GEMM，复用权重

当 M>8 时，同一个权重 tile 被多个 token 使用，arithmetic intensity 随 M 增长。实现分两步：

  1. FP32 基线先实现 128-thread 的二维 tiled GEMM，保持结果可对照。
  2. 执行图稳定后，使用 FP16 operands + FP32 accumulation 接入 Metal 4 matmul2d / cooperative tensor。
M5 MPP 起点 值 含义
SIMD tile 32 × 32 每个 SIMD group 负责一个输出 tile
SIMD groups / threadgroup 2 × 2 = 4 128 threads；组合成约 64 × 64 threadgroup 输出 tile
K tile 128 Apple 针对 M5 16-bit GEMM 给出的起始建议
Operand source Direct device memory 先让硬件 cache 工作，不默认复制 A/B 到 threadgroup memory

这一点修正了“prefill 必须把 A、W 都手工搬进 threadgroup memory”的过度概括。 Apple 的 M5 MPP 指南明确建议，优化 GEMM 可以先直接从 device memory 读取并依赖 cache；只有格式转换、量化解码或 profiler 证明有收益时才显式 staging。

M=9..31 使用普通 tiled GEMM；M≥32 且维度对齐时尝试 MPP。LM head 在当前 run_layers() 中只计算最后一个 token， 即使刚完成 prefill，它仍走 M=1 GEMV。

3. ds4：可迁移的是方法，不是模型特例

本节对照 antirez/ds4@c463029 的 Metal 实现。ds4 面向 DeepSeek V4 的 MoE 图，规模和算子都不同； 但它对提交边界、M 分段和数据流融合的处理，可以直接验证本文的主线。

ds4 做法 源码证据 TinyLlama 迁移
批量复用一个 command buffer 和 compute encoder g_batch_cb / g_batch_enc 实现 begin_step / encode / end_step；op wrapper 不自行等待
M=1、M=2..8、大 M 分别走 matvec、 small-batch matvec、matmul shape dispatch 采用同样的三段 dispatcher，不再只判断 M==1
Decode 用 4–8 SIMD groups 协作 2 个输出行 matvec dispatch FP32 TinyLlama 从 8 groups、256 threads、NR=2 起步
大 prefill 使用 Metal 4 matmul2d，128 threads / 4 SIMD groups，并按 32/64/128 token tile 选择 pipeline direct-RHS MPP 在 FP16 阶段增加 MPP 快路径；FP32 和非对齐 shape 保留 fallback
Gate/up dot product 后直接计算 SwiGLU fused gate/up/SwiGLU 保留两股权重读取，但删除独立 SwiGLU pass 和 gate/up reread
RMSNorm+weight、Q/KV norm、FlashAttention 使用专用融合 kernel norm / attention 融合 reduction 后自然相邻的逐元素操作；attention 不落完整 score matrix
M5 的 GPU-only scratch 使用 StorageModePrivate private scratch workspace/KV 在无需 CPU 访问时可评估 private；readback buffer 保持 shared
ds4 最值得复制的不是某个 tile 常量，而是它把 shape 当作 dispatch contract： 每条路径都有明确适用范围、function constants、pipeline cache 和 fallback。

不直接复制的部分

ds4 的 routed MoE、SSD expert streaming、压缩 KV、Q2/Q4/IQ2 格式和模型专用 attention 不属于 TinyLlama。它们证明了“量化解码应融入消费权重的 kernel”， 但不能成为本轮引入复杂度的理由。

4. 融合：先消除边界，再消除中间数据

第一层：提交合并

把所有 op 编码进同一个 command buffer/serial compute pass，即使 kernel 一个都不改， 也能立即删除每个 op 的 command buffer 创建、提交和 CPU wait。这是第一优先级。

第二层：kernel 与数据流融合

候选 具体设计 决定
Q + K + V 加载时打包为 [2560,2048]，一次 matmul 读取 normed input， 输出使用 view 分成 Q/K/V；后续可在 epilogue 做 RoPE 和 KV write。 做
Gate + Up + SwiGLU 打包为 [11264,2048]，一次 matmul 生成成对结果， epilogue 直接计算 silu(gate) * up。 做
O / Down + residual 在 matmul epilogue 中加 residual，删除独立 add dispatch 和中间写回。 做
Decode attention 将 KV write、QK、online softmax、PV 合并为 decode 专用 kernel， 避免 materialize attention scores。 做，排在 matmul 之后
Final RMSNorm + LM head 单独计算每行 RMS scale；LM-head GEMV 在读取 input 时乘 scale， 不写 normalized hidden buffer。 做
RMSNorm + 整个 projection 每个 projection output group 若重复计算 RMS reduction，会放大工作量； 跨 threadgroup 共享 scale 又需要额外阶段。 不直接融合
融合不是 dispatch 越少越好。若融合导致寄存器压力过高、occupancy 降低， 或在每个输出 group 重复 reduction，就应保留一个小 kernel 和明确的中间边界。

5. 精度：为什么放在最后

FP16 会把常驻权重从 4.098 GiB 降到约 2.049 GiB，并把 decode 的最低权重流量 从 3.854 GiB/token 降到约 1.927 GiB/token， 所以它最终一定重要。但如果先切 FP16：

  • 每 op wait 和大量 command buffer 仍然存在。
  • decode GEMV 的跨行 stride 访存仍然存在。
  • Q/K/V、gate/up 和 residual 的重复读写仍然存在。
  • 数值误差会让 kernel 重构更难调试。

因此精度策略是：先保持 FP32 建立正确基线；执行结构和 kernel mapping 稳定后， 再采用 FP16 weights/activations + FP32 accumulation/reduction。 量化是下一份独立设计，不混入本轮。

实施顺序

1

重做 execution lifetime

增加 begin_step / encode_op / end_step，删除 op 内 commit_and_wait；复用 command buffer 相关状态和临时 buffer。

2

建立三路 matmul dispatcher

M=1 使用 SIMD32 K-reduction GEMV；M=2..8 使用 small-batch GEMV；更大的 M 使用 FP32 tiled GEMM。

3

打包 projection 并加入 epilogue

依次完成 QKV、gate/up+SwiGLU、O/down+residual、final norm scale+LM head。

4

重写 decode attention

单 kernel 完成 KV append、online softmax 和 value reduction；保持 KV cache 布局对 head 维连续读取。

5

切换 FP16 并接入 Metal 4 MPP

在相同执行图上切 FP16 storage、保留 FP32 accumulation，并为对齐 prefill shape 增加 matmul2d 快路径。最后再讨论 INT8/INT4。

验收标准

Benchmark 在这里是验证工具，不是发现上述结构问题的前提。每一步只回答四个问题：

  1. 输出是否与 FP32 CPU/reference 在误差范围内一致。
  2. 一个 decode token 是否只发生一次 command buffer 提交和一次必要的 CPU wait。
  3. GPU capture 中是否消除了目标中间 buffer 和独立 dispatch。
  4. 真实模型 shape 的 prefill latency 与 decode token/s 是否改善，且无回退。
