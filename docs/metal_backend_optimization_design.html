Metal Backend Optimization

这份文档记录 tinyinfer 在 Apple M5 上从逐算子同步、单线程点积， 逐步演化到 step 级提交、SIMD32 GEMV、small-M tiled GEMM 和算子融合的过程。 重点不是背诵 tile 常量，而是学习如何从矩阵形状和硬件层级推导 kernel。

Status: Implemented Hardware: Apple M5 · 8-core GPU Model: TinyLlama 1.1B · FP32 Updated: 2026-06-07

1. 结果与核心判断

阶段 核心变化 Prefill Decode
最初实现 每 op commit + wait；每个输出由一个线程串行计算 K 186.6 ms 139.7 ms/token · 7.16 token/s
Step batching + GEMV 一个推理 step 一次提交；M=1 使用 SIMD32 reduction 121.8 ms 44.7 ms/token · 22.39 token/s
Register-tiled small-M 一个权重值同时服务 4 个 token 约 55.1 ms M=1 路径不变
BK=128 + threadgroup X tile 4 个 SIMD groups 显式共享 X[4,128] 约 46–48 ms 约 45 ms/token，存在运行噪声
Reduction 与融合 并行 RMSNorm、LM head+argmax、residual add+RMSNorm 约 41–47 ms 约 44–48 ms/token

Benchmark 为短 prompt 单机测量，会受温度、系统负载和 GPU 竞争影响。 最后两阶段区间有重叠，因此不宣称无法稳定复现的小幅加速。

最确定的第一问题：同步

算子依赖需要 GPU 顺序，不需要 CPU 每个 op 等待。提交边界应是推理 step，而不是算子。

Decode 的核心：M=1

它是 GEMV。权重几乎没有跨 token 复用，目标是连续读取和尽可能接近内存带宽上限。

Prefill 的核心：复用

M 增大后，同一权重可服务多个 token。tile 的意义是把这种复用映射到寄存器和片上内存。

融合不是目标

只有在减少实际内存流量、dispatch 或无效计算，并且不严重降低 occupancy 时才值得融合。

2. 建立 M/N/K 坐标系

TinyLlama 的线性层统一写成：

X[M,K] × W[N,K]ᵀ → Y[M,N]

M = 同时处理的 token 数
N = 输出元素 / 权重行数量
K = 每个输出点积的长度
维度 决定什么 优化问题
N 有多少个相互独立的输出点积 如何分给 threadgroup 和 SIMD group
K 每个点积需要多少乘加和内存读取 如何分给 32 lanes，是否按 BK 分块
M 同一权重能被多少 token 重用 选择 GEMV、small-M GEMM 或完整 tiled GEMM

本机硬件约束

项目 本机值 设计含义
GPU Apple M5 · 8 GPU cores 需要发出足够多的 threadgroups 供硬件持续调度
SIMD width 32 lanes 点积沿 K 按 32 lanes 分工，使用 simd_sum
Threadgroup memory 32 KiB 用于显式共享 X tile 或 reduction scratch，不应无目的地搬运所有数据
Memory model Unified memory 不存在每 token 从 RAM 上传到独立显存；成本来自 DRAM/cache 到执行单元的数据流
推导顺序： 先看输出空间 [M,N] 如何切给 threadgroups，再看一个输出点积如何沿 K 切给 lanes，最后决定哪些数据值得放入寄存器或 threadgroup memory。

3. 实际优化路径

1

把提交边界从 op 提升到 step

原实现中，每个 op 创建 command buffer 和 encoder，随后 commit + waitUntilCompleted。这把 GPU 工作强制串成大量 CPU/GPU 往返。 

旧：
RMSNorm → commit/wait
Q matmul → commit/wait
K matmul → commit/wait
...

新：
encode all ops in one serial encoder
→ encode final token selection
→ commit once
→ CPU waits only when token id is needed

后端通过 pending command buffer/encoder 自动批量编码； argmax、host copy 和显式 synchronize() 是 flush 边界。

同一 serial compute encoder 已提供 dispatch 顺序。模型依赖不等于需要 CPU 等待。
2

M=1：SIMD32 GEMV

Decode 的输出公式为：

out[n] = Σ x[k] × W[n,k]

一个 SIMD group → 一个 out[n]
32 lanes → 沿 K 分工
simd_sum → 合并 32 个 partial sum

当前一个 threadgroup 含 4 个 SIMD groups，因此一次计算 4 个 N 输出：

output_index =
    threadgroup_id * outputs_per_threadgroup
    + output_in_threadgroup

lane 0  handles k = 0, 32, 64, ...
lane 1  handles k = 1, 33, 65, ...
...
lane 31 handles k = 31, 63, 95, ...

K % 4 == 0 时使用 float4，每 lane 一次处理 4 个 FP32。 否则走标量 fallback。最后不足 4 个 N 输出由边界判断处理。

Decode 从约 139.7 ms/token 降到 44.7 ms/token。

3

Small-M：4×4 register tile

Prefill 的第一版 tile 让一个 threadgroup 负责 Y[4,4]： 4 个 SIMD groups 各负责一个 N 列，每组同时累加 4 个 M 行。 

threadgroup_id.y → output_row_begin = tile_y * 4
threadgroup_id.x → output_col tile
simdgroup_id     → tile 内的一个 output_col
lane_id          → 沿 K 分工

一个 weight value
→ 同时用于 4 个 token 的 partial_sums[0..3]

这一步没有使用 threadgroup memory，主要收益来自寄存器中的权重复用。 它适合短 prefill，避免传统大 GEMM tile 在小 M 下大量空置。

4-token prefill 从约 121.8 ms 降到约 55.1 ms。

4

沿 K 分块：BK=128 + shared X tile

Register-tiled kernel 已显式复用权重，但 4 个 SIMD groups 仍会分别读取同一份 X。 因此只把真正跨 SIMD group 重复的数据 X 放入 threadgroup memory： 

BM = 4
BN = 4
BK = 128

for k_begin in [0, K) step 128:
    128 threads cooperatively load X[4,128]
    threadgroup_barrier()

    each SIMD group loads one W[col,128]
    and computes four output rows

    threadgroup_barrier()

X[4,128] 为 2 KiB。权重没有跨 N 列共享，因此仍直接连续读取， 不为了形式上的“完整 tile”额外搬入 threadgroup memory。

含 barrier 的 kernel 中，尾部越界 SIMD group 不能提前 return； 它必须参与 barrier，只是不执行有效计算。

Prefill 进一步稳定到约 46–48 ms。

5

RMSNorm：从单线程串行扫描到 threadgroup reduction

原 RMSNorm 每一行只有一个线程串行扫描 hidden 两次。新实现让一个 256-thread threadgroup 负责一行：

  1. 每个线程按 stride 256 累积平方和。
  2. 每个 SIMD group 使用 simd_sum 得到局部和。
  3. 第一个 SIMD group 归并 8 个局部和并计算 scale。
  4. 256 个线程并行写归一化结果。

这是 reduction 并行化，不是跨算子融合。它先修复单个 op 内部确定存在的串行瓶颈。

6

LM head + Argmax：消除 logits 中间张量

推理只需要最大 token id，并不消费完整的 32,000 logits。因此新增 matmul_argmax： 

stage 1:
LM-head GEMV
→ each threadgroup writes one local (value, index)

stage 2:
one threadgroup reduces all local pairs
→ writes final token id

tie 时选择最小 index，保持原 argmax 语义。这样不再分配、写入和读取完整 logits， workspace 也删除了 max_seq_len × vocab 的预留。

端到端收益有限，因为 LM head 的主要成本仍是读取约 250 MiB FP32 权重； 但执行图更正确，也能随词表增长更好地扩展。

7

Residual Add + RMSNorm：融合真正相邻的数据流

Transformer 中 residual add 后紧接 RMSNorm。融合 kernel 一次读取主分支和 residual， 将相加结果保留到 residual 输出并暂存在 threadgroup memory，再完成 reduction 和 norm： 

value = residual_out[i] + residual[i]
residual_out[i] = value
row_values[i] = value
sum_sq += value * value

reduce sum_sq
norm_out[i] = row_values[i] * scale * weight[i]

当前两条 residual 链都使用 fused op。第一层 attention norm 单独执行； 之后每层末尾直接产生下一层 norm。最后一层只对最后 token 执行 add + final RMSNorm。

这一步删除了 engine hot path 中的独立 add kernel，但短 workload 的端到端结果仍落在 测量噪声范围内，因此记录为结构优化，而不是宣称显著吞吐提升。

4. 如何判断是否值得融合

融合需要同时回答三个问题：

  1. 是否减少了 device memory 的实际读写，而不仅是少了一个函数调用？
  2. 是否消除了 dispatch 或 CPU/GPU 边界？
  3. 增加的寄存器、threadgroup memory 和控制流是否会降低 occupancy？
候选 判断 结论
Residual Add + RMSNorm 严格相邻；相加结果会立刻被 norm 再读；可在片上复用 已实现
LM head + Argmax 完整 logits 无消费者；可以只保留局部最大值 已实现
Gate + Up + SwiGLU 可删除 gate/up activation 写读并共享 X，但两套巨大权重仍必须读取 暂缓，按 M benchmark
RMSNorm + 所有 projection 可能让每个输出 group 重复计算 norm，或需要跨 group 共享 scale 不直接融合
Attention 内部融合 当前 score 被重复计算三次；online softmax 可消除大量重复计算 下一阶段高优先级

为什么 Gate + Up + SwiGLU 不一定明显加速

Decode 中 gate/up activation 每层只有约 22 KiB，而两套 FP32 权重各约 44 MiB。 即使完全消除 activation 写读，主要权重流量仍然存在。融合后还会增加两个 accumulator 和两股权重流，可能提高寄存器压力。

Prefill 更可能受益，因为 X tile 可以加载一次同时服务 gate/up。 正确做法是保留现有路径，新增 fused pipeline，并对 M=1/4/8/16 分别 benchmark 后再决定 dispatcher。

5. 正确性与 benchmark 方法

每次优化都先增加形状测试

  • GEMV：M=1,K=8,N=5，覆盖 N 尾部。
  • Small-M GEMM：M=5,N=6,K=8，覆盖 M/N 双尾块。
  • BK tiled：M=5,N=6,K=256，覆盖两轮 BK=128。
  • Fused argmax：覆盖最大值和相同最大值时选择较小 index。
  • Fused add+norm：分别检查 residual 输出和 norm 输出。

端到端验证

cmake --build build -j
ctest --test-dir build --output-on-failure

./build/run_token_ids_smoke \
  --backend metal \
  models/TinyLlama-1.1B-Chat-v1.0 \
  16 2 1 15043 29892 590

CPU 与 Metal 对同一 prompt 均生成 1024 338。 这不是完整数值等价证明，但能捕获很多会改变模型执行图的错误。

性能测量纪律

  • GPU benchmark 必须串行运行；并行运行两个进程会争用同一 GPU。
  • 记录同一命令、同一 prompt、同一 max sequence length。
  • 短 workload 至少复测两次，报告区间，不把单次最低值当结论。
  • 理论分析用于选择方向，benchmark 用于判断实现是否真的更快。
  • 端到端没有改善时，保留结构变化必须有明确理由，例如减少 workspace 或改善扩展性。

6. 容易混淆的硬件概念

一次 dispatch 不只计算 4 个输出

一个 threadgroup 计算 4 个输出，但一次 dispatch 会启动 ceil(N / 4) 个 threadgroups。GPU core 并发或分批执行它们。

K 很大时不是重新启动 kernel

SIMD group 沿 K 的多轮循环仍属于同一次 kernel、同一个 SIMD group。 partial sum 保存在寄存器里；每轮只加载下一段 K 数据。硬件可能在等待内存时切换到其他 resident SIMD group，但程序语义上没有重新 dispatch。

Unified memory 不等于不需要带宽

权重加载后常驻 unified DRAM，不会每 token 通过 PCIe 上传到 GPU。 但每次 matmul 仍要通过 memory controller 和 cache hierarchy 将需要的数据送到执行单元。 Decode 的模型工作集远大于片上 cache，因此权重 streaming 仍然昂贵。

Threadgroup memory 只存有明确复用的数据

在 small-M kernel 中，X 被多个 N 列重复使用，因此值得显式 staging。 每个 N 列的权重不同，没有跨 SIMD group 复用，因此直接连续读取更简单。 “把 A 和 B 都搬到 shared memory”不是普遍真理。

7. 当前 dispatcher 与执行图

matmul_out(M, N, K):
    if M == 1:
        SIMD32 GEMV
    else if M <= 16 and K % 128 == 0:
        small-M GEMM, BM=4, BN=4, BK=128
        X staged in threadgroup memory
    else if M <= 16:
        register-tiled small-M GEMM
    else:
        generic matmul fallback
one inference step:
    encode embedding
    encode layer operations into one serial encoder
    use fused residual add + RMSNorm between blocks
    final token only:
        fused add + final RMSNorm
        fused LM-head GEMV + argmax
    commit once
    wait for token id
当前实现的核心价值不是拥有很多 kernel，而是每条路径都有明确 contract： 适用形状、硬件映射、fallback、正确性测试和 benchmark 证据。

8. 下一阶段

1

重写 Attention

当前每个输出元素为了 max、denominator 和 value reduction 重复计算三次 attention score。优先改成每个 query/head 协作计算，并使用 online softmax 保存 score 统计。

2

为 M > 16 实现真正的大 tiled GEMM

当前大 M 仍使用通用 fallback。需要独立选择 BM/BN/BK、寄存器 tile 和 threadgroup memory 策略，而不是继续放大 small-M kernel。

3

使用硬件计数器验证瓶颈

用 Xcode GPU Capture / Metal System Trace 检查 device memory bandwidth、 cache hit、ALU utilization、occupancy 和 stall 原因。端到端计时无法解释所有问题。

4

最后再改变精度

在执行结构稳定后评估 FP16 weights/activations + FP32 accumulation。 量化会直接减少 decode 权重流量，但不应掩盖同步和 kernel mapping 问题。
