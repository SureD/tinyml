TinyInfer Benchmark Design

Design doc for a small phase-level benchmark used to measure TinyInfer prefill and decode latency before and after future Metal backend work.

1. Context And Scope

TinyInfer now has a CPU f32 correctness backend and a LLaMA-style inference path. The next major learning target is Metal optimization. Before optimizing kernels, the project needs a repeatable way to measure whether a backend change improves real inference behavior.

The first benchmark should be intentionally small. It should measure model phases, not individual operators. This keeps the benchmark easy to maintain while still answering the questions that matter during early Metal bring-up:

  • How long does prefill take?
  • How long does decode take per generated token?
  • Does a backend change improve end-to-end inference time?
  • Does decode latency grow as KV cache length grows?

2. Goals

  • Provide a simple CPU backend baseline for inference latency.
  • Use the same benchmark shape for future Metal backend comparisons.
  • Measure prefill and repeated decode_one separately.
  • Keep tokenizer and model loading outside inference timing.
  • Use fixed token ids so runs are deterministic and independent from Python.
  • Print compact CSV output suitable for manual comparison and shell scripts.
  • Avoid new dependencies and avoid a benchmark framework in v1.

3. Non-Goals

  • No per-operator benchmark in v1.
  • No flamegraph, timeline trace, or UI.
  • No tokenizer performance measurement.
  • No model loading time mixed into inference metrics.
  • No multi-batch, request scheduling, or serving benchmark.
  • No statistical benchmark dependency such as Google Benchmark.
  • No new core runtime profiling API in the first implementation.

4. Proposed Interface

Add one developer executable: 

build/bench_infer <model_dir> <backend> <max_seq_len> <max_new_tokens> <token_id> [token_id...]

Example: 

build/bench_infer models/TinyLlama-1.1B-Chat-v1.0 cpu 128 8 1 15043 29892 590 1024 338
Argument Meaning Reason
model_dir Local Hugging Face model directory. Reuses the existing safetensors/config loader path.
backend cpu in v1, metal later. Keeps backend comparison explicit at the command line.
max_seq_len KV cache capacity for this run. Controls memory plan and decode cache length limit.
max_new_tokens Number of measured decode tokens. Controls the measured decode loop length.
token_id... Fixed prompt tokens. Avoids tokenizer dependency and makes benchmark inputs reproducible.

5. Fixed Case Runner

bench_infer is a manual measurement harness. The project-level benchmark entry should be a fixed case runner: 

python3 scripts/bench_infer_cases.py --backend cpu

The case runner owns the official benchmark inputs. It should use fixed prompt lengths, fixed decode lengths, and fixed seeds to generate legal token ids. Token semantics are not important for TinyInfer performance because the model executes the same kernel shapes regardless of the actual token values.

Case Prompt length Max seq len Decode tokens Seed
p16_d8 16 128 8 0xC0FFEE10
p64_d8 64 128 8 0xC0FFEE40
p128_d8 128 256 8 0xC0FFEE80

The runner should print one CSV row per case and include the case name and seed. Progress messages go to stderr so stdout remains machine-readable CSV.

6. Benchmark Flow

The executable should load the model once, run a short untimed warmup, reset engine state, then run one measured inference case. 

create backend
load model
run warmup:
  prefill(prompt)
  decode_one(...) for a small number of tokens

engine.reset()
time prefill(prompt)
time decode_one(...) for max_new_tokens
print CSV

A reset measured state keeps the KV cache simple: every measured run starts from an empty cache, then advances through prefill and decode exactly once.

LlamaInferEngine::reset() clears workspace and KV cache state while preserving loaded weights, so warmup does not require reloading the checkpoint.

7. Metrics

The fixed case runner should print one CSV header and one CSV row per case. 

case,seed,backend,prompt_len,max_seq_len,max_new_tokens,prefill_ms,decode_total_ms,decode_ms_per_token,tokens_per_sec
p16_d8,0xc0ffee10,cpu,16,128,8,1200.412,9400.733,1175.092,0.851
Metric Definition Notes
prefill_ms Wall-clock time for one prefill(prompt). Measures prompt processing and KV cache initialization.
decode_total_ms Total time for all measured decode_one calls. Includes the growing KV cache scan during generation.
decode_ms_per_token decode_total_ms / max_new_tokens. Main decode latency number for simple comparisons.
tokens_per_sec max_new_tokens / (decode_total_ms / 1000). Useful for quick throughput intuition.

8. Timing And Synchronization

Use std::chrono::steady_clock for wall-clock timing. The benchmark should time only inference calls, not argument parsing, tokenizer work, model loading, or printing. 

start timer
engine.prefill(prompt, next_token)
backend.synchronize()
stop timer

start timer
for each generated token:
  engine.decode_one(previous_token, next_token)
backend.synchronize()
stop timer

On CPU, synchronize() is a no-op. On Metal, it must wait for queued GPU work to finish. This is important because timing only command submission would make Metal numbers look faster than real execution.

v1 should run one short warmup before measuring. Multiple repeats and percentile reporting can wait until the simple benchmark stops being enough.

9. Input Cases

The C++ benchmark accepts token ids directly. The fixed case runner generates deterministic legal token ids from each case seed and the model vocabulary size. A Python tokenizer may still be used for manual smoke tests, but tokenizer work should not be part of timed inference.

Case Values Purpose
Official v1 prompt length 16, 64, 128 Small enough to run on scalar CPU while still showing prefill scaling.
Official v1 decode length 8 Enough to average several decode steps without making CPU runs too painful.
Deferred larger cases prompt_len=512, max_new_tokens=32 Add after Metal kernels exist or when long-context behavior becomes the target.

10. Implementation Plan

Add one source file and one CMake target: 

tests/cpp/bench_infer.cc
add_executable(bench_infer tests/cpp/bench_infer.cc)
target_link_libraries(bench_infer PRIVATE tinyinfer)
target_compile_options(bench_infer PRIVATE -Wall -Wextra -Wpedantic)

Add one fixed case runner: 

scripts/bench_infer_cases.py

Keep helper code local to the executable:

  • parse_u32
  • create_backend
  • validate_prompt
  • run_warmup
  • run_measured
  • print_csv

The benchmark result can stay as a small local struct: 

struct BenchResult {
    const char* backend = nullptr;
    uint32_t prompt_len = 0;
    uint32_t max_seq_len = 0;
    uint32_t max_new_tokens = 0;
    double prefill_ms = 0.0;
    double decode_total_ms = 0.0;
};

11. Validation And Errors

The benchmark should fail early and loudly for invalid setup.

  • Reject empty prompts.
  • Reject prompt length plus generated tokens greater than max_seq_len.
  • Reject token ids greater than or equal to vocab_size.
  • Reject unsupported backend names.
  • Print backend or loader failures directly to stderr.

Verification for the benchmark itself should be lightweight: build the target, run it on a small prompt, and confirm that the CSV row is printed and decode produces valid token ids.

12. Alternatives Considered

Alternative Decision Reason
Start with per-operator profiler. Defer. Useful later, but too much machinery before whole-model Metal impact is visible.
Use Google Benchmark. Defer. The first benchmark needs one executable and CSV output, not a new dependency.
Benchmark text prompts through Python tokenizer. Reject for timed path. Tokenizer overhead is not part of backend inference performance.
Add runtime profiling callbacks. Defer. The core runtime should stay simple until phase-level numbers are insufficient.

13. Risks

  • Single-run numbers may be noisy. This is acceptable for v1; repeat/median can be added later.
  • Reloading the model for warmup and measurement is slow. It is outside timed inference and keeps state management simple.
  • Metal numbers will be wrong if synchronize() does not wait for GPU completion.
  • Whole-model timing will not explain every bottleneck. Operator microbenchmarks should be added when that becomes a real blocker.

14. Future Work

  • Multiple repeats with min, median, and p90.
  • JSON output in addition to CSV.
  • Separate prefill-only and decode-only modes.
  • Per-operator microbenchmarks for matmul and attention.
  • Optional Metal command-buffer GPU timestamps.
  • Larger optional case matrix for long-context decode.

These should be added only after the simple phase-level benchmark stops being enough.
